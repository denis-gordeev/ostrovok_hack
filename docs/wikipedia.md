# Русская Википедия и локальный GraphRAG

Корпус — существующие статьи основного пространства русской Википедии в пределах
двух **исходящих** ссылок от «Казани». Перенаправления разрешаются бесплатно
для глубины обхода; циклы и отсутствующие страницы не добавляются. Ссылки из
навигационных шаблонов тоже входят в дамп и могут вести к общим темам.

Снимок зафиксирован: **20261001**. `wiki_download.py` проверяет завершённость
заданий, размеры и SHA1 каждого файла по официальному `dumpstatus.json`.
Скачиваются `page`, `linktarget`, `redirect`, `pagelinks`, `imagelinks` и
`pages-articles-multistream.xml.bz2`. XML читается потоково. На диске остаются
только выбранные тексты, исходная gzip-викиразметка, версии, граф и имена файлов;
исходные дампы сохраняются для воспроизводимости и повторного запуска.

## Поиск

- `cointegrated/rubert-tiny2`, ревизия
  `e8ed3b0c8bbf4fb6984c3de043bf7d2f4e5969ae`, 312 измерений, CPU.
- Для короткого текста: нормализованный CLS, как в карточке модели. Для длинного:
  окна по 512 токенов с перекрытием, нормализованное среднее CLS всех окон.
  Это наше допущение агрегирования; вход не обрезается молча.
- Минимальный индекс: **один вектор на статью**, заголовок + первые 1200 символов.
  Он ускоряет поиск по теме статьи, но не заменяет векторы каждого фрагмента.
- Весь очищенный текст разбит на фрагменты с перекрытием и включён в SQLite FTS5
  с русским Snowball-стеммингом. Совпадения в глубине статьи остаются доступны.
- Начальные статьи — объединение FAISS и FTS через reciprocal rank fusion.
  Фрагменты сначала объединяются по статье; точные совпадения заголовков получают
  приоритет, чтобы длинная статья не вытесняла остальные своими фрагментами.
  Нужный подробный фрагмент получает собственный RuBERT-вектор при запросе;
  эти векторы тоже кэшируются на диске.
- Обход выполняет **`langchain-graph-retriever` 0.8**, `GraphRetriever` + `Eager`,
  через адаптер к SQLite/FAISS. Узлы — статьи; `IdEdge` — реальная исходящая ссылка.
  До двух переходов при запросе, ограниченное число возвращаемых фрагментов.
  Рёбра не извлекаются и не описываются через LLM.

Генеративная модель для загрузки, графа и индексации не вызывается. Существующий
агент использует свою LLM для итогового ответа по найденным данным.

## Инструменты

- `wikipedia_search(query, limit=6)` — поиск с обходом графа; цитируемые фрагменты,
  исходные и постоянные ссылки на ревизии, дата снимка и ограничения.
- `wikipedia_article(title, offset=0, max_chars=6000, image_offset=0)` — чтение
  полного очищенного текста с пагинацией и ссылок на файлы по 20 за страницу.

Изображения не скачиваются. Сохраняются имена из `imagelinks` и URL
`Special:Redirect/file/...`, который разрешает файл через MediaWiki, в том числе
с Commons. Это ссылка-резолвер, а не зафиксированный бинарный URL или версия
картинки. Страница описания файла нужна для проверки существования, авторства
и лицензии; наличие имени в `imagelinks` само по себе их не подтверждает.

Текст доступен с указанием статьи, постоянной ссылки, истории авторов и лицензии.
Очищенная викиразметка не воспроизводит отрисовку шаблонов; исходник сохраняется.
Энциклопедия не является источником актуальных часов работы, цен, ограничений
проезда или координат для карты. Геометрию агент проверяет через OSM.

## Файлы и кэш

Вне Git, на VPS: `/opt/ostrovok/.cache/server/wikipedia/ruwiki-20261001/`.

- `dumpstatus.json`, исходные `.sql.gz`, `.xml.bz2`, `download-complete.json`;
- `inventory.sqlite` — служебное соответствие названий/ID и редиректов;
- `building.sqlite` — незавершённый корпус, `corpus.sqlite` — опубликованный;
- `vectors.sqlite`, `index.faiss`, `index.json` — локальные векторы и индекс;
- `encoder-cache/`, `query-cache/` — векторы по хэшу текста и полному контракту модели;
- `status.json`, `embedding-status.json` — ход построения.

Модель хранится отдельно в `.cache/server/models/`. Индекс включает fingerprint
модели, pooling, размера окна и снимка. После смены модели или правил индексации
нужен отдельный каталог и перестроение. Готовый корпус и индекс публикуются
переименованием временных файлов; незавершённые данные не выдаются за готовые.

`scripts/wiki_prefetch.py` — необязательный помощник: одновременно с извлечением
текстов заполняет тот же кэш векторов. Он не публикует индекс. Основной индексатор
после сборки корпуса проверяет полный набор и досчитывает недостающие векторы.
SQLite WAL позволяет читать уже сохранённые фрагменты, не блокируя извлечение;
перед публикацией корпуса выполняется checkpoint. Помощник не нужен для
корректности и может быть перезапущен: результат определяется хэшами текста.

## Запуск

```sh
# Только необходимые сервисы; порт эмбеддингов доступен лишь на loopback VPS.
docker compose -f docker-compose.yml -f deploy/compose.langgraph.yml \
  -f deploy/compose.transit.yml -f deploy/compose.wikipedia.yml up -d --build

# Исходные дампы; загрузка возобновляется через HTTP Range.
python scripts/wiki_download.py \
  --folder .cache/wikipedia/ruwiki-20261001 --snapshot 20261001
uv run python scripts/wiki_ingest.py \
  --folder .cache/wikipedia/ruwiki-20261001 --snapshot 20261001
uv run python scripts/wiki_embed.py \
  --folder .cache/wikipedia/ruwiki-20261001 --url http://127.0.0.1:8082
```

На VPS общая папка сервисов — `.cache/server`, поэтому для команд выше
использовать `.cache/server/wikipedia/ruwiki-20261001`, а не `.cache/wikipedia`.

Для инструментов: `WIKIPEDIA_DATA_DIR` указывает на каталог корпуса;
`EMBEDDINGS_URL` — на локальную модель. В Docker это `http://embeddings:8082`,
на хосте — `http://127.0.0.1:8082`. Публичного порта модели нет.
Контейнер модели ограничен 1 GiB RAM и одним CPU; сборка запускается отдельно
с ограничением памяти/CPU и не загружает модель в процесс агента.

После построения векторов автоматически выполняются проверки поиска по Кремлю,
Кул-Шарифу и Татарской слободе, постоянных ссылок на ревизии, чтения текста и
ссылок на изображения Казани. Отчёт — `validation.json`; неуспешная проверка
не оставляет индекс отмеченным как готовый. Эти проверки не вызывают LLM.

В зафиксированном дампе отобрано **93 038 статей**, включая корневую:
461 357 текстовых фрагментов, 10 459 255 направленных связей между статьями,
1 306 477 связей статья–файл. Пропущенных текстов нет; у «Казани» 89 ссылок
на файлы. Это число связей, а не уникальных изображений во всём корпусе.
Проверенные запросы про Кремль, Кул-Шариф и Старую Татарскую слободу возвращают
соответствующую статью первой; на прогретом сервере проверка занимала около
0,5–0,7 секунды на запрос. Это измерения трёх запросов, не гарантия для любых вопросов.

Защищённый Basic Auth статус: `GET https://188.241.197.121:8443/knowledge/status`.
Во время сборки на VPS также доступны `docker logs ostrovok-wikipedia-build` и
`docker logs ostrovok-wikipedia-embed`. После успешного завершения временные
контейнеры удалены, логи сохранены в каталоге снимка: `build.log`, `embed.log`,
`prefetch.log`. Пока сборка не завершена, инструмент
сообщает о неготовности; готовность проверяется отдельно для корпуса и векторов.
Повторный запуск готового корпуса — без изменений. Не удалять данные для обновления
на месте: собирать новый снимок отдельно.

Проверки: `uv run python -m unittest discover -s tests -v`.

## Сводка по цели запроса

Оба инструмента принимают опциональный `purpose` (1–2000 знаков): зачем
основной модели нужны данные и какие факты она ищет. Без него выдача прежняя.
С ним отдельный нестриминговый вызов LLM суммаризует только полученные
фрагменты (до 6000 знаков на источник, до 8 источников для поиска).
Основная модель получает `summary` и `sources` с номерами, ссылками,
версиями и атрибуцией, без исходных текстов. Пагинация статьи сохраняется;
сводка относится только к текущей странице. Ошибка суммаризации не
подменяется передачей полного текста. Сводка генеративная, её можно
проверить повторным вызовом без `purpose`. Это дополнительный платный
вызов: те же LLM_API_KEY/LLM_API_URL, модель WIKIPEDIA_SUMMARY_MODEL
или LLM_MODEL; таймаут 60 с, без повторов. Выдержки отправляются этому
провайдеру. Индексация и извлечение графа по-прежнему не используют LLM.
