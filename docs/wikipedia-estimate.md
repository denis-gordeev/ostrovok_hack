# Оценка корпуса русской Википедии: два перехода от «Казани»

## Уточнение: предпочтителен готовый дамп

Первоначальные 1–4 дня ниже относятся к постраничной загрузке через REST API.
Для массовой выгрузки предпочтительнее дампы одного фиксированного снимка:

1. `page`, `pagelinks`, `linktarget`, `redirect` — выбрать существующие статьи
   основного пространства в двух переходах от «Казани», разрешая редиректы.
2. Потоково прочитать `pages-articles-multistream.xml.bz2`, сохраняя только
   выбранные статьи и версии. Полностью распаковывать XML на диск не нужно.
3. Очистить викиразметку для поиска; отдельно сохранить исходный wikitext.
4. Через `imagelinks` выбрать имена файлов для нужных статей. URL и лицензионные
   сведения получать пакетами только для этих файлов; локальный `image` не
   содержит метаданные всех файлов Wikimedia Commons.
5. Построить дисковый индекс и граф ссылок без массовой LLM-экстракции.

Проверенный каталог дампов на 27.10.2026 содержит: multistream XML 6,21 GB,
`page` 315 MB, `pagelinks` 933 MB, `linktarget` 243 MB, `redirect` 39 MB,
`imagelinks` 95 MB. Итого около 7,8 GB скачивания для этих файлов. Это десятичные
единицы и размеры сжатых файлов. `latest` может содержать файлы разных дат:
для реализации обязательно фиксировать один завершённый снимок и его суммы.

Сетевое время 7,8 GB при устойчивых 20–100 Mbit/s — примерно 52–10 минут,
без учёта ограничений источника и протокольных накладных расходов. Сверху нужны
декомпрессия, SQL/XML-разбор, очистка и индексация. Их время на VPS пока не
измерено: несколько часов — рабочая гипотеза, а не обещанный срок.
LLM-стоимость зависит от метода индексации, способ скачивания её не меняет.

Источник размеров: https://dumps.wikimedia.org/ruwiki/latest/

## Первоначальная оценка постраничной загрузки

Дата: 27.10.2026. Пока выполнена только оценка, полная выгрузка и GraphRAG
не запущены. «Два перехода» здесь — исходящие ссылки на существующие статьи
основного пространства имён; не входящие ссылки, не категории и не внешние сайты.
Ссылки, добавленные навигационными шаблонами, также увеличивают корпус.

## Измерения

Получен HTML статьи «Казань» через REST API. Из её 881 ссылки случайно выбраны
40 статей (`random.Random(42)`). Их полные HTML сохранены с gzip в
`.cache/wiki-probe/`; там же `estimate.py`, `sample.json`, `measurements.json`.
Это исследовательский кэш, не готовый пользовательский индекс.

| Метрика | Результат |
|---|---:|
| Прямые ссылки из «Казани» | 881 |
| Разные адресаты ссылок из 40 статей | 6053 |
| Среднее число ссылок на статью в выборке | 198,7 |
| Средний текст | 16 707 символов / 29 287 байт UTF-8 |
| Средний gzip текста | 8021 байт |
| Средний gzip HTML | 38 250 байт |
| Средний объём текста в o200k_base | 5312 токенов |
| Среднее число изображений после удаления навигации | 23,9 |
| Среднее время HTTP-запроса с локальной машины | 1,31 секунды |

Это выборка первого уровня, а не случайная выборка всего будущего корпуса.
Токенизатор целевой модели может отличаться. При разборе прототип исключал
заголовки с двоеточием; корректная полная выгрузка должна определять namespace
через MediaWiki API, учитывать перенаправления, красные ссылки и канонические ID.
Поэтому приведённые количества не являются точной переписью Википедии.

## Предварительный бюджет

Для планирования: **30–150 тысяч статей**. Это широкий инженерный ориентир,
не статистический доверительный интервал. Простое умножение 881 × 198,7 даёт
около 175 тысяч ссылок до удаления дублей; дедупликация может сильно уменьшить
результат. Точный размер станет известен после обхода ссылок первого уровня.
На него влияют снимок, шаблоны, namespace и обработка перенаправлений.

При размере статей как в выборке:

- Тексты UTF-8: около **0,9–4,4 GB**, gzip текстов **0,24–1,2 GB**.
- Сохранённый gzip HTML: ещё **1,1–5,7 GB**.
- Плановый бюджет вместе с графом, полнотекстовым индексом, метаданными
  изображений и запасом: **5–20 GB**, без плотного векторного индекса и
  без скачивания самих изображений. Это оценка, не измеренный размер индекса.
- Тексты: примерно **160–800 млн токенов** по использованному токенизатору.
- При последовательных запросах с паузой и наблюдаемой задержкой:
  ориентировочно **1–4 дня**, с возобновлением после ошибок. Время на VPS
  и действующие ограничения сервиса могут отличаться.

На текущем VPS около 60 GB свободного диска. Кэш и дисковый поиск помещаются
без покупки дополнительной машины. Индексацию вести потоково с ограничением
памяти, чтобы не мешать OTP и агенту. GPU для графа ссылок и SQLite FTS не нужен.

## Два разных значения GraphRAG

1. **Поиск с расширением по графу ссылок.** Узлы — статьи, рёбра — реальные
   гиперссылки. Текст режется на фрагменты; полнотекстовый поиск (позднее при
   необходимости эмбеддинги) находит исходные статьи, затем граф добавляет
   релевантных соседей. Модель отвечает по фрагментам с URL и версиями источников.
   Платных LLM-вызовов на построение такого графа **нет**. Это graph-aware RAG,
   а не стандартная LLM-экстракция Microsoft GraphRAG. Ссылка не доказывает
   конкретное семантическое отношение между объектами.
2. **Standard Microsoft GraphRAG.** LLM извлекает сущности, отношения, описания
   и отчёты сообществ. Его стоимость определяется фактическими входными и
   выходными токенами, числом проходов, моделью и повторными запросами.
   Для иллюстрации, на тарифе $0.10 / миллион входных и $0.40 / миллион
   выходных токенов: 300 млн входных + 100 млн выходных стоят $70;
   1 млрд + 300 млн — $220. Это арифметические сценарии, не замер и не смета
   полной индексации. Несколько проходов, отчёты и более дорогая модель
   могут поднять стоимость до сотен долларов и выше.

Предпочтительный старт: сохранить полный корпус в два перехода и использовать
граф ссылок без массовой LLM-обработки. Для вопросов агента отдавать небольшой
релевантный подграф, а не весь корпус. Тематически общие статьи не запрещать,
но учитывать близость к Казани и содержание при отборе контекста.

Сохранять URL статьи, revision ID, дату получения, историю авторов и лицензию.
Для изображений — URL файла/миниатюры и страницу описания, где указаны авторство
и лицензия конкретного файла; не считать все изображения одинаково свободными.
