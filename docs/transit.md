# Общественный транспорт: Bustime → GTFS → OpenTripPlanner

## Что запущено

Агент вызывает `transit_route`, который обращается к нашему HTTP
`POST http://188.241.197.121:8080/transit/route`. API использует локальный
OpenTripPlanner 2.10.0 с GTFS и вырезкой OSM Казанской агломерации. Внешние транспортные API
во время расчёта не вызываются. Сеть маршрутов позволяет искать пересадки
и пешие подходы по OSM.

```json
{
  "start": {"lat": 55.871472, "lon": 49.222008},
  "end": {"lat": 55.774239, "lon": 49.093396},
  "departure_time": "2026-10-27T09:00:00+03:00"
}
```

Время отправления необязательно: без него используется начало следующей
минуты по Москве. Явное время должно содержать часовой пояс. За пределами
календаря модели возвращается 422, а не выдуманное расписание.

В ответе до трёх вариантов: номера маршрутов, остановки посадки/высадки,
времена, пересадки и геометрия участков (encoded polyline). `duration_minutes`
считается от фактического начала варианта, `initial_wait_minutes` — ожидание
до его начала, `total_minutes_from_requested_departure` — до прибытия от
запрошенного времени. Ожидание при пересадках входит в длительность варианта.
`contains_transit=false` означает только пеший вариант. Пустая выдача
не доказывает отсутствие общественного транспорта в реальности.
В ответ инструмента агенту геометрия не включается.

## Ограничения модели

**Это не официальное полное расписание.** Источник:
https://sel.bustm.net/static/other/db/v8/current/10.json

Проверенный снимок загружен 26.10.2026. Исходник и его SHA-256 сохранены.
Текущий объединённый экспорт: 92 маршрута, 1491 остановка, 20 892 рейса, 690 567 stop_times.
Включены активные нескрытые автобусы, троллейбусы, трамваи и метро,
с пригодными отправлениями и остановками внутри расширенной области.
Включены пригодные пригородные поезда и дополнения 106/108 и 407.
Источники, ограничения и сборка дополнений: [региональные маршруты](regional-routing.md).
Самолёты и речные рейсы не включены.
Непригодные/неоднозначные записи пропускаются с подсчётом в отчёте.
Экспорт не гарантирует полноту сети. В частности, кольцевые отправления,
для которых ID остановки не определяет однозначную позицию, исключаются.

- Для Bustime отправления сохраняются; времена промежуточных и конечных
  остановок **рассчитываются**, `timepoint=0` в GTFS.
- Скорости для моделирования: автобус 18, троллейбус/трамвай 16, метро 32 км/ч;
  плюс 20 секунд на остановку. Это допущения, а не измерения.
- Длина берётся по геометрии Bustime, если порядок проекций остановок
  согласован. Для 7 направлений использованы прямые между остановками;
  при расчёте времени их длина умножена на 1.25. Это отмечено в отчёте.
- Маски дней проецируются на локальный календарь **27.10–25.11.2026**.
  Это 30-дневный горизонт прототипа, а не подтверждённый срок действия источника.
  Праздники, исключения, отмены и задержки неизвестны. GPS не используется.
- Расчётное время пересадки может оказаться недостаточным в реальности.
  Доступность для колясок не проверяется.

MIT-лицензия репозитория Bustime относится к исходному коду; лицензия на базу
данных отдельно не установлена. Снимок и GTFS не включаются в Git.

106/108 сохраняют опубликованные времена обоих концов рейса; для 407 прибытие
модельное, а ежедневность — неподтверждённое допущение. Геометрия дополнений
модельная, промежуточная посадка не заявляется.

## Конвертация

```bash
# Уже скачанный JSON можно использовать повторно без сети.
uv run python scripts/bustime_to_gtfs.py \
  --source .cache/research/bustime/kazan-city.json \
  --output .cache/transit/kazan.gtfs.zip \
  --start-date 2026-10-27 --days 30
uv run python -m unittest discover -s tests -v
```

Рядом с ZIP создаётся `kazan.gtfs.json`: происхождение, контрольные суммы,
календарь, параметры модели, статистика и пропуски. Для локального API также
положите исходный JSON в `TRANSIT_DATA_DIR/bustime-source.json` для ссылок
на маршруты. Скрипт не скачивает данные автоматически и не продлевает
календарь в фоновом режиме. Для обновления сначала получите свежий снимок.

Архив проверен MobilityData GTFS Validator 8.0.1: **нет ошибок**. Есть
предупреждения: повторяющиеся точки геометрии, короткий горизонт календаря,
отсутствие контакта издателя и регистр имён. Это не проверка точности
расписания и не устраняет ограничения модели.

## Сервер и повторная сборка

Все файлы на VPS: `/opt/ostrovok/data/transit-regional-v1/`:
`bustime-source.json`, `kazan.gtfs.zip`, `kazan.gtfs.json`, `kazan.osm.pbf`,
`graph.obj`, `validation/`. OSM взят из расширенной вырезки ПФО с проверкой целостности дорог.

Сначала скопируйте конвертированный ZIP, JSON-отчёт и исходный снимок на VPS.
Для замены снимка остановите OTP и API на время согласованного обновления
либо подготовьте новый каталог отдельно. После изменения GTFS пересоберите
граф и пересоздайте OTP и app. Не подменяйте JSON-отчёт без соответствующего графа.

```bash
cd /opt/ostrovok
# При первом запуске / после обновления данных:
docker run --rm --name ostrovok-otp-build \
  -e JAVA_TOOL_OPTIONS=-Xmx4g \
  -v /opt/ostrovok/data/transit-regional-v1:/var/opentripplanner \
  opentripplanner/opentripplanner:2.10.0 --build --save
# Все сервисы, включая transit:
docker compose -f docker-compose.yml -f deploy/compose.langgraph.yml \
  -f deploy/compose.transit.yml up -d --build
docker compose -f docker-compose.yml -f deploy/compose.langgraph.yml \
  -f deploy/compose.transit.yml ps
```

OTP ограничен heap 4 GiB / контейнером 5 GiB. Порт 8090 опубликован только
на loopback; наружу запросы идут через существующий geo API с прежним
ограничением клиентских IP. Внутри Docker: `OTP_URL=http://otp:8080`,
`TRANSIT_DATA_DIR=/app/transit-data`. Вне Docker по умолчанию:
`OTP_URL=http://127.0.0.1:8090`, `TRANSIT_DATA_DIR=.cache/transit`.

Планы сохраняются в `.cache/transit-plans/`. Ключ включает SHA-256 GTFS,
параметры, явное время и версию клиента. Неудачные/пустые результаты не
кэшируются. Общий бесконечный HTTP-кэш агента для `/transit/route` отключён.
GTFS, OSM и граф сохраняются при перезапуске контейнеров.
