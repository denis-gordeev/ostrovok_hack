# Проект

- Регион прототипа — Казань и агломерация: Свияжск, Иннополис, Зеленодольск, аэропорт.
  Границы и версия данных заданы в region_config.py; при смене снимка менять
  пространство кэшей. Авто использует граф всей области, чтобы не обрезать объезды.
- Цель — агент для получения проверяемых географических характеристик через OpenStreetMap.
- Единый LangGraph-агент: геоданные, маршруты, Википедия, отели из снимка ostrovok.ru, модель шума и события KudaGo.
- Кэшировать внешние геоданные и результаты запросов на диске в `.cache/`; путь настраивается через `CACHE_DIR`. Не коммитить кэш и секреты.
- Не выдумывать географические факты. Различать отсутствие данных и отсутствие объекта. Указывать источник и время получения данных.
- Сохранять реализацию простой; не добавлять сервисы и инфраструктуру без необходимости.
- Общественный транспорт: Bustime JSON → модельный GTFS → локальный OpenTripPlanner.
  Не выдавать расчётные времена промежуточных остановок за официальное расписание;
  явно указывать неполное покрытие, отсутствие задержек и календаря праздников.
  Исходные снимки, GTFS и графы хранить вне Git; сохранять происхождение и контрольные суммы.
- Интерфейс: карта MapLibre/deck.gl + диалог; подробность шагов по умолчанию — «Кратко»,
  также доступны «Подробно» и «Отладка». Скрытые рассуждения модели не показывать.
- Маршруты: по умолчанию рассчитывать и показывать пеший и транспортный варианты.
  Для загородных поездок за пределами пешего лимита — авто и общественный транспорт;
  автомобильный лимит 150 км по прямой, фактическая дорога может быть длиннее.
  Пеший — основной только при длине пешего пути строго меньше 1 км; от 1 км
  основной — общественный транспорт. Явный выбор пользователя имеет приоритет.
  Пеший вариант от OTP не выдавать за транспорт; отсутствие варианта объяснять.
- Автомобильные маршруты: driving_route / OSMnx drive, оценка времени без пробок.
  Не выдавать за пошаговую навигацию: поворотные и условные ограничения не учтены.
- Пригородные GTFS: включать железную дорогу и пригодные междугородние маршруты;
  106/108 импортируются из опубликованного расписания Иннополиса, 407 — с сайта музея.
  Для 407 ежедневность — неподтверждённое допущение; всегда сообщать ограничение.
  Дополнительные автобусные геометрии модельные, промежуточная посадка не заявляется.
- Управление картой — через update_map по data_ref проверенного результата инструмента.
  Последние результаты и изменения запроса отображать автоматически, без подтверждения;
  устаревшие слои заменять, связанные визуализации обновлять согласованно.
  Геометрию хранить в артефактах/состоянии графа, не раздувать контекст модели.
  Конусы иллюстративные, не выдавать их за рассчитанную видимость или измеренную высоту.
- Энциклопедические данные: фиксированный дамп русской Википедии, исходящие
  ссылки в два перехода от Казани с разрешением редиректов. Тексты, исходная
  викиразметка, версии, граф и ссылки на файлы хранятся на диске вне Git.
  GraphRAG — через langchain-graph-retriever, локальную rubert-tiny2 и FTS;
  LLM не используется для извлечения графа или индексации. Вектор начала статьи
  дополняется поиском по полному тексту. При смене модели/снимка менять индекс.
  Википедия не заменяет актуальные часы работы и данные OSM для маршрутов.
  Ссылка между статьями не доказывает смысловое отношение; указывать источники,
  версии и дату снимка. Ссылки на изображения вести на страницы с лицензиями.

```sh
uv sync --python 3.12
# Только если .env ещё нет: скопировать .env.example и заполнить значения.
# LLM_API_KEY, LLM_API_URL (без /chat/completions), LLM_MODEL.

npm --prefix web ci

# UI: http://127.0.0.1:2024/ui/
```

Маршрутам нужны OSMnx API и OTP; энциклопедии — готовый корпус и сервис
эмбеддингов. Пути и адреса: `CACHE_DIR`, `OVERPASS_URL` (с `/api`, без
`/interpreter`), `OSMNX_API_URL`, `OTP_URL`, `TRANSIT_DATA_DIR`,
`EMBEDDINGS_URL`, `WIKIPEDIA_DATA_DIR`. Локальный `.env` не перезаписывать.
Геопорты VPS ограничены списком клиентских IP: при отказе сначала проверить
доступ/туннель, а не делать API общедоступным.

```sh

node --test web/tests/*.test.js

```

До слияния integration проходили 46 Python-тестов и 4 JS-теста; готовый корпус

## Обновление существующего VPS

Сначала проверить ветку, изменения и актуальные конфиги. Не предполагать, что
всё уже закоммичено: последние изменения региона и Википедии были развёрнуты
из рабочего дерева. Не делать reset/clean, не включать кэш и секреты в Git.

Перенос кода из локального корня проекта (сохраняет серверные данные и `.env`):

```sh
rsync -az --exclude='.git/' --exclude='.env' --exclude='.env.*' \
  --exclude='.secrets/' --exclude='.cache/' --exclude='data/' \
  --exclude='.venv/' --exclude='.langgraph_api/' --exclude='__pycache__/' \
  --exclude='web/node_modules/' --exclude='web/dist/' \
  ./ root@188.241.197.121:/opt/ostrovok/
```

Не добавлять `--delete` и не копировать локальный `.env` поверх серверного.
Команда переносит текущее рабочее дерево, включая незакоммиченный код:
перед запуском проверить состав файлов. Она не подготавливает новый пустой VPS.

На сервере использовать **все четыре Compose-файла**, пути считать от корня:

```sh
cd /opt/ostrovok
compose() {
  docker compose -f docker-compose.yml -f deploy/compose.langgraph.yml \
    -f deploy/compose.transit.yml -f deploy/compose.wikipedia.yml "$@"
}
compose ps
# Обычное обновление приложения; Docker сам собирает web/dist.
compose up -d --build app langgraph
# Если менялся сервис модели / его Dockerfile:
# compose up -d --build embeddings
# После пересоздания LangGraph обновить DNS upstream в Nginx:
compose exec -T langgraph-gateway nginx -s reload
compose ps
compose logs --tail=100 app langgraph embeddings langgraph-gateway
```

При обновлении всей конфигурации: `compose up -d --build`.
Для изменения переменных `.env` нужно пересоздание соответствующего контейнера;
обычного restart недостаточно. В контейнере адреса — `http://overpass/api`,
`http://app:8080`, `http://otp:8080`, `http://embeddings:8082`;
их задаёт Compose. Не подставлять localhost вместо соседнего контейнера.
Это dev-сервер LangGraph с одним одновременным запуском, не production-кластер.

После деплоя проверить health контейнеров, HTTPS с проверкой сертификата,
401 без авторизации, UI и `/knowledge/status` с авторизацией
(`corpus_ready=true`, `semantic_ready=true`). Сделать небольшой запрос поиска,
проверить текст/ссылку на ревизию и отображение результата на карте для геозапроса.
Не ограничиваться статусом «контейнер запущен».

Не запускать `down -v`, очистку каталогов или повторную инициализацию Overpass
для обычного обновления кода. Перестройка OTP и Википедии — отдельные долгие
операции; сначала подготовить новый каталог, проверить результат, затем переключить
Compose/переменные. Сохранять старый рабочий набор для отката.

`OSTROVOK_TEST_DSN` и отдельную тестовую базу. Не направлять их в рабочую БД.

в Docker адрес БД — `ostrovok-db:5432`, не localhost:5433.
Перенос исходников не означает наличие подготовленных шумовых данных или
ключа провайдера hotel-agent: их готовность проверять отдельно.


## Единый агент и фильтр шума

`hotel_geo_tools.py` использует клиенты из `src/hotel_agent`, но общий граф,
LLM_API_* и состояние карты — из `agent.py`. Отели сохраняются как проверенные
артефакты `data_ref`, координаты для последующих маршрутов читаются через
`read_geo_result`; источником этих точек является снимок отелей, а не OSM.
В Казани фильтр применяется программно ДО выдачи модели и карты:
`max(day.score, night.score) <= 50`. Отели без оценки не рекомендуются как
прошедшие фильтр. Проверяются до 30 кандидатов, сортировка по максимуму двух
индексов, при равенстве сохраняется исходный порядок. Другие города Татарстана
не покрыты шумовой моделью и возвращаются с явным ограничением.
При пустой выдаче возможен один повтор с расширением заданного радиуса;
бюджет, даты и город не меняются, расширение явно указывается в ответе.

Модель шума на сервере: `.cache/server/kazan_noise-v1/`, в контейнере
`KAZAN_NOISE_DATA_DIR=/app/.cache/kazan_noise-v1`. Результаты оценок кэшируются
в `.cache/server/noise-reports/` с идентичностью файлов модели и сетки.
Подготовка — `scripts/prepare_noise.py` внутри образа приложения с монтированным
кэшем и сетью Compose. Он обращается к своему Overpass без areas, получает
здания по bbox границы, считает полную H3-сетку только внутри Казани.
Не заменять её тестовой выборкой: это исказит перцентильную шкалу 0–100.
Сырые ответы, NPZ, provenance и контрольные суммы — вне Git. В статическом
Overpass нет meta: возраст строек неизвестен; не выдавать модель за измерения.
Снимок KudaGo может быть пустым: это не означает отсутствие событий в Казани.

## Быстрые составные запросы

- По умолчанию до 12 вызовов модели, 48 инструментов, 12 каждого инструмента,
  до 8 одновременно. Настройки AGENT_MAX_* в `.env.example`.
- Географические гипотезы разрешено сразу проверять по названиям в OSM
  параллельно с Википедией и search_web. Не использовать выдуманные координаты
  и не утверждать историческую связь по одному совпадению названия.
- Нет дат отелей — продолжить независимую часть задачи и уточнить даты в ответе;
  не подставлять даты или возраст детей. История/OSM не должны ждать этого уточнения.
- `overpass_query` имеет отдельный общий бюджет 6 попыток; HTTP 200 с timeout
  remark также повторяется. Неполные данные не считать результатом и не кэшировать.
- Веб-поиск — `web_tools.py`, DDGS, ключ не требуется; отдельный дисковый кэш
  с TTL 6 часов. Поисковые сниппеты — недоверенные выдержки, не прочитанные страницы.
  Из их адресных подсказок можно формировать OSM-запрос, но не геометрию маршрута.
- Многоэтапные маршруты — plan_route для участков, затем compose_routes по
  проверенным ссылкам и update_map одним слоем. Геометрическое объединение не
  подтверждает стыковку расписаний; время зависимых транспортных этапов считать
  последовательно. При ошибке одной точки завершать остальные части запроса.
- Оценки шума сохраняются и по отдельным точкам: смена состава подборки не требует
  повторного расчёта уже проверенных отелей при неизменных файлах модели.

- `context_memory.py` не принимает пустое LLM-резюме: сохраняет текущий запрос,
  пары AI tool_calls/ToolMessage и компактные выдержки с точными data_ref.
  При таком сбое диалог переключается на детерминированное сжатие без повторных
  пустых LLM-сводок. Не заменять всю историю пустым running_summary.
- При затянувшемся геопоиске туристического маршрута (8 Overpass-вызовов и
  минимум 2 проверенных POI) модель переводится от общего поиска к расчёту,
  чтению проверенных результатов и обновлению карты. Неподтверждённые точки
  не включать как доказанные исторические места.


### Проверка широкого сценария

Запрос «построй туристический маршрут + подбери отели по местам банды Тяп-Ляп»
проверен на VPS: первый пакет — Wikipedia + search_web + Overpass; затем
получены проверенные места, рассчитаны два участка 568,8 и 383,0 м, выполнены
compose_routes и update_map. Отсутствие дат отелей не остановило маршрут.
Отдельный поиск с датами 19–22 ноября и радиусом 3 км вернул 3 кандидата с
индексами шума <=50. Это проверка прототипа, не гарантия наличия/исторической
связи каждого современного здания. 474 Python-теста и 4 JS-теста проходят.
