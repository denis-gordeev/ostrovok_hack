# Геоагент для Казани

Минимальный агент на LangGraph: модель выбирает инструменты, получает реальные
данные OpenStreetMap и формулирует ответ с источниками. В общем диалоге доступны поиск отелей, модель шума и события KudaGo.
В Казани поиск программно исключает отели с дневным или ночным индексом шума
выше 50/100 и кандидатов без оценки. Это модельный индекс, не децибелы.

Веб-интерфейс: карта слева, диалог и шаги агента справа, слои мест, маршрутов
и иллюстративных 3D-конусов. [Запуск и команды карты](docs/map-ui.md).
Поддерживаются пешие, автомобильные и транспортные маршруты; для авто время
оценивается без пробок, результат не заменяет пошаговую навигацию.
Покрытие расширено до Свияжска, Иннополиса и Зеленодольска;
[региональные маршруты и ограничения расписаний](docs/regional-routing.md).

## Запуск

Нужны Python 3.11+ и [uv](https://docs.astral.sh/uv/).

```bash
uv sync --python 3.12
cp .env.example .env
# Заполнить LLM_API_KEY в .env
uv run python agent.py
uv run python agent.py 'Найди парки и крупные дороги рядом с 55.7961, 49.1064' --stream
```

В `.env` можно изменить `LLM_MODEL` (по умолчанию `gpt-4.1`),
`LLM_API_URL` для совместимого API (по умолчанию `https://api.openai.com/v1`,
без `/chat/completions`), `OVERPASS_URL` (базовый URL с `/api`,
без `/interpreter`), `REQUEST_TIMEOUT` в секундах и `CACHE_DIR`.
Для маршрутов задайте `OSMNX_API_URL=http://188.241.197.121:8080`
либо адрес собственного OSMnx HTTP API (по умолчанию `http://127.0.0.1:8080`).
Модель должна поддерживать tool calling. Внешним API нужен доступ в интернет.

## LangGraph CLI и Studio

После настройки `.env` запустите локальный сервер:

```bash
uv run langgraph dev
```

Откройте ссылку на Studio из вывода команды и выберите граф `geo_agent`.
Конфигурация находится в `langgraph.json`, точка входа — `langgraph_app.py`.
Локальное состояние сервера хранится в `.langgraph_api/` и не коммитится.

## Инструменты

- `transit_route(start_lat, start_lon, end_lat, end_lon, departure_time)` —
  общественный транспорт Казани через локальный OpenTripPlanner. Отправления
  из Bustime, промежуточные времена расчётные; есть пересадки и пешие участки.
  Это модельный прототип с неполным покрытием, без задержек и календаря праздников.
  [Данные, GTFS и запуск](docs/transit.md).

- `walking_route(start_lat, start_lon, end_lat, end_lon)` — пеший маршрут
  между координатами в Казани: длина, время при 4.5 км/ч и смещения до узлов
  графа. Концы — до 10 км друг от друга по прямой. Смещения не включены в длину;
  доступность для колясок не проверяется. Геометрия опущена в ответе инструмента;
  полный GeoJSON доступен через HTTP `POST /route`.
- `search_osm(lat, lon, tags, radius_m, limit)` — OSMnx: объекты в радиусе
  до 15 км, OSM-теги, ссылки, расстояния до геометрии по прямой в метрах.
  Например, `{"leisure": "park"}` или `{"highway": ["primary", "secondary"]}`.
  Несколько ключей тегов объединяются через **OR**.
- `overpass_query(query, limit)` — произвольный Overpass QL с JSON-выводом.
  Можно искать объекты и получать информацию по OSM ID. Запросы ограничивайте
  небольшим радиусом или bbox; `limit` ограничивает выдачу модели, а не серверный
  объём запроса. При наличии `remark` результат считается неполным и возвращается ошибка.

Прямой вызов без LLM и ключа:

```bash
uv run python - <<'PY'
from geo_tools import search_osm, overpass_query
print(search_osm.invoke({
    "lat": 55.7961, "lon": 49.1064,
    "tags": {"leisure": "park"}, "radius_m": 500,
}))
print(overpass_query.invoke({
    "query": '[out:json][timeout:60];nwr(around:500,55.7961,49.1064)[highway=primary];out center tags;'
}))
PY
```

Граф: `START → agent → tools → agent → … → END`. Есть `invoke` и `stream`;
программно агент доступен через `from agent import build_agent`.
Ошибки инструментов передаются модели, успешные результаты содержат
`source`, `endpoint`, `retrieved_at`, `cache_hit`. Выдача ограничена 30 объектами
по умолчанию (до 100); поля `total` и `truncated` показывают усечение.

## Файловый кэш

Всё хранится в `.cache/` (или `CACHE_DIR`), не коммитится:

- `http.sqlite` — успешные HTTP GET/POST через requests, включая Overpass;
- `osmnx/` — штатный кэш сырых ответов OSMnx;
- `features/`, `overpass/` — обработанные результаты с исходной датой получения.

Повторный идентичный геозапрос берётся с диска, включая после перезапуска.
Ключ включает сервер, параметры и теги. Ошибки не сохраняются как результаты.
Автоматического срока истечения пока нет: дата в ответе позволяет увидеть возраст
данных. Для полного обновления удалить каталог `CACHE_DIR` при остановленном агенте.
Вызовы LLM не кэшируются. Подложки карты пока нет, тайлы не скачиваются;
будущие загрузки через requests будут попадать в общий HTTP-кэш.

Расстояния `search_osm` не являются пешими маршрутами; для них используйте
`walking_route`. Например: «Построй пеший маршрут из 55.7961, 49.1064
в 55.7905, 49.1144. Укажи длину и время». Пустая выдача означает отсутствие
данных в OSM, а не отсутствие объекта. Близость дороги не подтверждает шум в номере.

Документация: [LangGraph](https://docs.langchain.com/oss/python/langgraph/quickstart),
[OSMnx](https://osmnx.readthedocs.io/en/stable/user-reference.html).

# hotel-agent

LangGraph-агент подбора отелей в Татарстане по снимку ostrovok.ru с оценкой шума в Казани по OpenStreetMap
и событиями Казани на даты поездки по афише KudaGo.

## Запуск

```bash
uv sync
cp .env.example .env                  # заполнить ключ LLM
uv run hotel-agent                    # чат в терминале
uv run pytest                         # тесты (без сети)
```

Агенту нужны данные: снимок островка в Postgres и снимок шума — см. «Данные островка» и «Шум в Казани» ниже.
Без них агент запускается, но соответствующий tool отвечает, что поиск или оценка недоступны.
События Казани агент загружает сам при запуске — см. «События Казани (KudaGo)».

## Граф

```
START → agent ─┬─ вызов tool → tools (ToolNode) → agent
               └─ ответ пользователю → END
```

- `agent` — LLM (`init_chat_model(HOTEL_LLM_MODEL)`) с привязанными tools; сегодняшняя дата (по Москве)
  попадает в её системный промпт. Агент сам решает: уточнить у пользователя или вызвать tool.
- Извлечение интентов (`src/hotel_agent/intents/`, LLM со structured output) сейчас отключено: код и тесты
  остались, но в граф узел не подключён. Включить обратно — узел `extract_intent` перед `agent`
  (`graph/builder.py`, `graph/nodes.py`), поле `intent` в `AgentState`, `intent_extractor` в `AgentContext`
  и `IntentExtractor` в `cli.py`.
- `search_hotels_in_tatarstan` — tool: подбор отелей Татарстана по снимку островка в Postgres
  (`OSTROVOK_DB_DSN`, см. «Данные островка» ниже). На вход — даты, город, взрослые, возрасты детей, номера,
  бюджет за ночь, звёзды, оценка, типы размещения, питание, бесплатная отмена, оплата на месте, удобства,
  точка и радиус, расстояние до метро, часть названия, сортировка. На выход — отели, свободные на все ночи,
  с ценой за период и самым дешёвым подходящим тарифом каждого номера; кандидаты кладутся в
  `state["hotel_candidates"]`. Цена номера на ночь = минимальная цена ночи × `price_ratio` тарифа опорной
  ночи того же типа (будни/выходные) и того же числа гостей; дети младше `free_child_age` отеля бесплатны;
  гости делятся по номерам поровну. Схемы запроса и ответа — `src/hotel_agent/apis/ostrovok/models.py`.
- `events_in_kazan` и `kazan_event_details` — tools событий Казани (схема `kudago` в Postgres, см. «События Казани
  (KudaGo)» ниже). Первый на даты поездки отдаёт до 5 разовых событий в эти дни и до 2 самых популярных выставок,
  второй — подробности события по id. Агент вызывает первый вместе с поиском по Казани и заканчивает ответ абзацем
  «Во время вашего визита будут проходить события: …» со ссылками на KudaGo (раздел 5.1 промпта).
- История хранится в checkpointer по `thread_id`.

## Трасса агента

`uv run hotel-agent` печатает в терминал (stderr) каждый вызов LLM и tool, а в конце хода — итог:

```
  [llm 1] deepseek/deepseek-v4-flash-0731  3.2s  in 6 410 · out 412 (размышл. 318) → search_hotels_in_tatarstan
  [tool] search_hotels_in_tatarstan  0.4s  {"checkin": "2026-11-01", "checkout": "2026-11-03", "city": "Казань"} → 18 342 симв.
  [llm 2] deepseek/deepseek-v4-flash-0731  4.1s  in 12 300 · out 1 020 (размышл. 260) → ответ
  ── ход: LLM ×2, tools ×1 · in 18 710 · out 1 432 (размышл. 578) · 7.9s
```

- `in` / `out` — токены входа и выхода вызова; `размышл.` — сколько из выходных ушло на размышление
  (reasoning). `н/д` — провайдер это число не сообщил (не путать с 0).
- После `→` у LLM — какие tools она вызвала (`×N` — несколько вызовов одного tool) или `ответ`.
- У tool — аргументы от LLM (в терминале обрезаны до 200 символов), время и размер ответа в символах:
  этот текст уйдёт во вход следующего вызова LLM. Ошибка tool показывается вместо размера.

Полная трасса пишется в `traces/<время запуска>.jsonl`, по JSON-строке на событие: `llm` (модель, время,
`input_tokens`, `output_tokens`, `reasoning_tokens`, `cache_read_tokens`, `tool_calls`), `tool` (`name`, `args`
целиком, `status`, `result_chars` или `error`) и `turn` (итог хода с текстом пользователя). Номер хода — поле `turn`.
Настройки: `AGENT_TRACE=false` выключает трассу, пустой `AGENT_TRACE_DIR` оставляет её только в терминале.
Код — `src/hotel_agent/tracing.py` (callback LangChain, подключается в `cli.ask`).

## Данные островка (Татарстан)

Отдельный пакет `src/ostrovok_scraper/`: сбор отелей Татарстана с внутреннего API ostrovok.ru (статика, цены по ночам, тарифы на 1–8 гостей, отзывы) в локальный Postgres. Сырые ответы лежат в схеме `raw`, нормализованные таблицы — в `ostrovok`. Дизайн: `docs/superpowers/specs/2026-10-26-ostrovok-scrape-design.md`.

**База со снимком без сбора.** `scripts/tools-db.sh` переносит данные tools в Postgres в Docker: схемы `ostrovok` и
`kudago` (`--with-raw` добавляет `raw`). Нужен только Docker.

```bash
scripts/tools-db.sh dump      # снять локальную базу (localhost:5433, --from DSN) в docker/initdb/02-tools-data.sql.gz
scripts/tools-db.sh up        # поднять ostrovok-db и залить снимок; --reset — заменить уже залитые данные
```

На новом томе снимок выполняется сам при первом `docker compose up` (как и `docker/initdb/01-test-db.sql`), поэтому
хватает файла снимка и `up`. Порт на хосте — `OSTROVOK_DB_PORT` (по умолчанию 5433); если он занят другим
контейнером, `up` назовёт его.

Сбор с нуля:

```bash
docker compose up -d                                       # Postgres (порт 5433)
uv run ostrovok-scrape db-init                             # миграции
uv run ostrovok-scrape all --limit-hotels 5 --nights 2     # пробный прогон
uv run ostrovok-scrape all                                 # полный сбор (≈1 ч)
uv run ostrovok-scrape normalize                           # пересобрать ostrovok из raw
uv run ostrovok-scrape report                              # сводка по raw и ostrovok
```

Отдельные шаги: `serp`, `serp-guests`, `hotels`, `child-age`, `rates`, `reviews`. Общие флаги: `--retry-failed`, `--limit-hotels N`, `--nights N`, `--today YYYY-MM-DD`. Сбор докачивается: перезапуск пропускает уже сохранённые ключи. При блокировке сайтом процесс завершается с кодом 2, сохранённое остаётся.

Островок иногда временно отдаёт тарифы отеля пустыми (`rates: null`) — такие ответы сохраняются как неполные и видны в `report` в колонке «неполных». Перезапросить их: `uv run ostrovok-scrape child-age --retry-failed`, `uv run ostrovok-scrape rates --retry-failed`, затем `normalize`. Часть `null` законна (у отеля нет номера на такой состав гостей) и останется неполной после повтора.

Тесты с БД (без переменной они пропускаются):

```bash
OSTROVOK_TEST_DSN=postgresql://ostrovok:ostrovok@localhost:5433/ostrovok_test uv run pytest
```

## События Казани (KudaGo)

Отдельный пакет `src/kudago_events/`: события Казани с официального публичного API KudaGo
(`kudago.com/public-api/v1.4/events/?location=kzn`) в схему `kudago` той же Postgres, что и снимок островка.
Дизайн: `docs/superpowers/specs/2026-10-28-kudago-events-design.md`.

**Загрузка.** `uv run hotel-agent` при запуске в фоновом потоке проверяет журнал `kudago.loads`: если удачной загрузки
не было больше суток (`KUDAGO_MAX_AGE_HOURS`), загружает события от сегодняшнего дня на 60 дней вперёд
(`KUDAGO_HORIZON_DAYS`). Чат при этом стартует сразу; пока данных нет, tool отвечает, что события не загружены, и
агент не пишет абзац. Новые данные заменяют старые одной транзакцией, а при сбое прежние остаются, ошибка печатается одной
строкой в stderr и пишется в `kudago.loads`.

```bash
uv run kudago-events load      # загрузить заново, даже если данные свежие
uv run kudago-events report    # число событий и сеансов, последние загрузки
uv run kudago-events db-init   # только миграции (загрузка применяет их сама)
```

**Сеть.** API KudaGo отвечает 403 с иностранных IP (в том числе через VPN). Процессу нужен российский IP: исключите
терминал из VPN или задайте `HTTPS_PROXY` — httpx подхватывает его сам. Страница `kzn.kudago.com/events/` не
используется: она закрыта проверкой от ботов.

**Отбор** (`src/hotel_agent/apis/kudago/select.py`). Визит — дни с заезда по выезд включительно, по Москве.
Разовое событие — все сеансы короче суток и их не больше 10 в окне загрузки (ежедневные экскурсии отсекаются).
Выставка — категория `exhibition` и сеанс длиннее суток или без конца. Прочие длинные события, акции (`stock`) и
деловые мероприятия (`business-events`) не показываются. Порядок — по числу добавлений в избранное на KudaGo,
одинаковые названия схлопываются; лимиты — 5 разовых и 2 выставки.

**Лицензия.** Данные KudaGo — по их открытой лицензии: у каждого показанного события должна быть прямая ссылка на его
страницу на kudago.com (tools отдают её в `url`), рекламные материалы использовать нельзя.

## Шум в Казани

Отдельный пакет `src/kazan_noise/`: относительная модель шума Казани по OpenStreetMap (дороги, рельсы, промзоны, аэропорт; экранирование зданиями и зеленью). Дизайн: `docs/superpowers/specs/2026-10-26-kazan-noise-design.md`. Агенту она доступна как tool `noise_in_kazan(points)`: до 30 точек `{lat, lon}` за вызов, ответ по каждой в том же порядке, точка вне Казани получает `error`.

```bash
uv run kazan-noise fetch      # скачать сырые данные OSM (публичные серверы Overpass: медленно, может понадобиться повтор)
uv run kazan-noise build      # собрать снимок объектов
uv run kazan-noise grid       # посчитать сетку H3 для шкалы баллов (--limit N — пробный прогон, сетка не сохраняется)
uv run kazan-noise query --lat 55.7963 --lon 49.1088 [--json]   # шум в точке
```

Данные лежат в `data/kazan_noise/` (путь — `KAZAN_NOISE_DATA_DIR`). Без снимка и сетки агент запускается, но tool отвечает, что оценка шума недоступна. Проверку модели запускает `uv run kazan-noise validate`: санити-проверки по снимку (у магистрали шумно, во дворах тише, в лесу тихо) и ранговая корреляция ночного балла с долей жалоб на внешний шум в отзывах островка; для второй части нужны `docker compose up -d` и собранный снимок островка. Код выхода 1, если санити-проверка не пройдена.

**Балл** — число 0–100: доля застроенных точек Казани, где тише (100 — громче всех), отдельно для дня (07–23) и ночи (23–07), с меткой от «очень тихо» до «очень шумно». Это относительная оценка, не децибелы. Для точки на здании (координаты отелей обычно стоят на здании) основной балл считается по самому шумному фасаду, а в `quiet_side` приходит оценка самой тихой стороны; днём и ночью эти фасады выбираются отдельно (ночью громче может быть двор с баром). Главные источники (`main_sources`) — до трёх с наибольшей долей энергии днём или ночью; участки одной улицы считаются одним источником.

Ограничения модели: уровни относительные, не дБ(А); потоки — значения по умолчанию для класса дороги, а не реальные замеры; нет отражений и метеоусловий; полнота OSM неравномерна по городу.
